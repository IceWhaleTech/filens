# 文档搜索实测：FiLens、ripgrep 与 git grep

**历史版本记录：** 本报告观测的是此前启用正文缓存和来源哈希的版本。当前源码版改为请求内存、不持久落盘、不计算来源哈希；新进程与 rg 的启动对照见[启动实测](agent-cli-search-startup.zh-CN.md)。下面保留原始观测，不能当成当前默认策略的时延。

这是 2026-10-29 在 Apple M4 Pro / darwin-arm64 上的**合成语料观测**。包含 108 个文件、96 条预先固定的查询，其中 72 条有答案、24 条无答案；按 12 个主题家族组织。原文与相关文件标签由开发者按构造规则指定，没有外部人工评审、留出集或 Agent 最终任务成绩。

FiLens 目前提供词项检索。下面同时公开精确命中、改写/跨语言失败、无答案误报和耗时，不能据此宣称优于语义搜索产品。原始配置、逐查询结果、哈希和指标见[完整 JSON](agent-cli-search-benchmark.json)，语料定义见[topics.json](../benchmarks/agent-search/topics.json)。

## 运行配置与公平性

- FiLens：源码构建的 BM25 默认模式、literal 模式，返回最多 10 个文件，使用完整提取文本；每次校验源文件 SHA-256。正文缓存不是常驻倒排或向量索引。
- ripgrep：ripgrep 15.2.0 (rev e89fff89ac)。literal 使用区分大小写的完整查询；词项 OR 使用忽略大小写的查询词，中文转相邻双字特征，英文去一小组停用词。词项规则固定在脚本中，没有按参考答案改写查询。
- git grep：git version 2.50.1 (Apple Git-155)，使用 `--no-index` 和同一组 OR 词项。
- 所有工具读同一份 UTF-8 文本。文件名是中性编号，不泄露主题；问题、标签、报告均在被搜目录外。源码及原始文档流程另列，不能用 rg 直接搜索 Office 二进制来制造优势。
- rg/git grep 没有相关性排序，候选按相对路径排序后取前 k 个，模拟有限上下文视图；FiLens literal 也以相同分数按路径排序，这三类配置的 MRR/nDCG 均留空。完整候选的召回/精确率另报。路径顺序不等于语义排名。
- 每个查询轮换五种配置的运行顺序，每次启动新进程。准确性语料先完成一次正文缓存准备：965.4 ms，写入 108 份正文缓存。查询时延包含该版本实际执行的 CLI 启动、遍历、提取/缓存处理、排序和序列化。

## 文件命中与误报

## 文件规模、首次使用和缓存

另生成 100、500、2000 个约 0.4 KiB 的短文本，查找唯一的 `SPEED2026`。每个规模先运行一次空正文缓存查询，再对每种配置重复 15 次并轮换顺序。这里“首次”仅清空 FiLens 缓存，**没有清空操作系统页缓存**。p95 使用 nearest-rank，15 个样本的尾部分位数仍很有限。

| 文件数 / 文本量 | FiLens 首次提取+查询（n=1） | FiLens 缓存 p50 / p95 | rg literal p50 / p95 | git grep OR p50 / p95 | 正文缓存 | FiLens 最大进程 RSS（单次） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 / 44.2 KiB | 801.3 ms | 456.9 / 463.1 ms | 6.9 / 9.9 ms | 15.1 / 16.0 ms | 75.4 KiB | 31.0 MiB |
| 500 / 221.2 KiB | 3247.1 ms | 1525.8 / 1569.8 ms | 15.0 / 20.5 ms | 21.5 / 24.2 ms | 377.0 KiB | 33.6 MiB |
| 2000 / 884.8 KiB | 12256.5 ms | 5526.9 / 6360.7 ms | 50.5 / 64.2 ms | 43.2 / 60.2 ms | 1507.8 KiB | 42.3 MiB |

macOS `time -l` 的最大进程 RSS 不是 supervisor 与 worker 并发内存之和。规模曲线主要反映短文本的遍历、文件哈希和缓存读写；大量 PDF、扫描件、慢盘和网络目录需要另测。FiLens 当前每次重新分块排名，尚未有常驻倒排索引，不能预期它具有 rg 的纯文本扫描速度。

规模重复的失败数：100 文件：FiLens BM25 0/15、rg literal 0/15、git grep 词项 OR 0/15；500 文件：FiLens BM25 0/15、rg literal 0/15、git grep 词项 OR 0/15；2000 文件：FiLens BM25 0/15、rg literal 0/15、git grep 词项 OR 0/15。上表缓存时延仅计算成功样本，实际 n 保留在 JSON 中。另有一次先导试跑在 2000 文件缓存查询时返回退出码 1，旧仪器没有保留错误响应，单独重放成功，原因尚未确认；该先导试跑没有并入完整重跑的分位数，也没有被当成成功。完整重跑保留操作错误，不自动重试。

## 修改与删除

一次修改后立刻查询旧值和新值，再删除并立即查询。各次都使用原有正文缓存：

| 操作 | 查询 | 命中文件数 | 耗时 |
| --- | --- | ---: | ---: |
| edit | UPDATE2026OLD | 0 | 199.8 ms |
| edit | UPDATE2026NEW | 1 | 198.5 ms |
| delete | UPDATE2026NEW | 0 | 200.1 ms |

这些结果验证下一次请求不继续返回旧内容；不代表实时监听或并发修改下的原子快照。

## DOCX、扫描 PDF 与图片

使用公开合成 DOCX、采购单 PNG，以及仓库两页扫描 PDF。rg 使用 **FiLens 同一提取器得到的完整文本**；提取成本 3694.6 ms（逐文件 CLI 启动，包含 OCR）单列，不能把下面 rg 的纯查询耗时当成从原始文档开始的总耗时。

| 原始文件 | 提取耗时 | 完整 | 字符数 |
| --- | ---: | --- | ---: |
| brief.docx | 180.8 ms | 是 | 112 |
| invoice.png | 489.5 ms | 是 | 205 |
| scan.pdf | 3024.3 ms | 是 | 75 |

| 查询 | 期望文件 | FiLens 命中 / 耗时 | rg 共享提取后命中 / 查询耗时 | FiLens 页码/坐标 |
| --- | --- | --- | --- | --- |
| BRIGHT2027 | scan.pdf | scan.pdf / 3105.0 ms | scan.pdf / 7.5 ms | 有 |
| 12345.67 | brief.docx, invoice.png, scan.pdf | scan.pdf, invoice.png / 222.7 ms | invoice.png, scan.pdf / 8.2 ms | 有 |
| FILENS2026 | invoice.png, scan.pdf | scan.pdf, invoice.png / 238.4 ms | invoice.png, scan.pdf / 7.3 ms | 有 |

FiLens 第一条搜索从空正文缓存开始，后两条复用正文。DOCX 的金额写成 `12,345.67`，这两种配置查询 `12345.67` 均未归一化千分位分隔符，因此漏掉 DOCX；扫描 PDF 和图片里的连续金额可命中。源码复核后修正了两项遗漏的扫描 PDF 相关标签，双方使用同一修正，原始查询、结果、时延不变；108 文件的固定检索标签没有修改。OCR 最大边长 960、OpenMP=2。仅检查已知编号/金额、完整性及定位字段，未在此量化 OCR 通用准确率或矩形精度；已有[OCR 质量样例](agent-cli-examples.zh-CN.md)另报错误。

## 本轮重复统计优化

上面的完整基线对应优化前的 WASM。在共享 WASM 核心中缓存有界的查询词频/分块长度，减少重复分词；literal 路径跳过不使用的 BM25 统计。缓存超过 8 MiB 的估算预算后退回原有路径，文件内容校验与排名公式保持一致。没有增加常驻运行时或持久倒排索引。

同一个 CLI、同一份语料、相互独立且已准备的正文缓存，轮换先后顺序：

| 范围 | 优化前 p50 | 优化后 p50 | 中位耗时变化 | 成功样本数（前 / 后） |
| --- | ---: | ---: | --- | ---: |
| bm25 | 598.6 ms | 381.7 ms | 下降 36.2% | 27 / 27 |
| exact | 202.3 ms | 202.0 ms | 下降 0.2% | 27 / 27 |
| bm25-2000 | 5308.3 ms | 2455.3 ms | 下降 53.7% | 5 / 5 |

按九类查询各重复三次，2000 文件查询重复五次；共 59 对成功请求逐字比较文件顺序、分数、证据和偏移，结果一致。记录 0 次失败；小样本不能保证稳定收益。完整采样和产物哈希见[优化观测](agent-cli-search-optimization.json)。这轮减少重复计算，尚未达到 rg 的原始文本扫描时延。后续按用户要求不持久落盘；最新启动优化、无哈希与无应用缓存的对照见[启动实测](agent-cli-search-startup.zh-CN.md)。更大的扫描收益应优先考虑请求内批处理或内存复用，并单独测量准备成本。



## 如何复现与扩展

```sh
npm run build:agent
npm run demo:agent -- --poster-only --lang en
node --test scripts/search-benchmark-metrics.test.mjs
node scripts/benchmark-agent-search.mjs
node scripts/write-search-benchmark-docs.mjs
```

需要 Node、rg、git；原文文档演示输入由 `npm run demo:agent -- --poster-only --lang en` 生成。也可用 `--binary /path/to/filens` 选择带 OCR 的源码构建。执行时避免同时编码 GIF、编译或运行其他基准。完整生成语料和缓存留在忽略的 `dist/agent-search-benchmark/`，报告和标签位于搜索根目录外。

zvec-grep 的固定参考提交为 `891497fa87d3e03d0c9273fed0ba3e75af62f179`，本轮**没有运行**。它具有 ripgrep、BM25、向量的混合路径，不能把这里的 rg 对照当成它的表现。下一步应在有许可的外部文档与人工留出问题上，按[评价方案](agent-cli-search-evaluation.zh-CN.md)补充持久索引、embedding 与完整 Agent 任务；先固定安装版本、模型和资源预算，再报告结果。
