# Agent 文档搜索：范围与客观评价方案

状态：完整评价设计方案，已有[FiLens、ripgrep 与 git grep 的合成语料实测](agent-cli-search-benchmark.zh-CN.md)，覆盖准确性、时延、规模、缓存更新和文档提取；不是外部真实语料或 Agent 完整任务成绩。源码版已补充[跨文件 BM25、精确匹配和文件名搜索](agent-cli-search.zh-CN.md)，以及按内容校验的正文缓存；常驻倒排/向量索引和 embedding 检索仍未实现。`summarize` / `prune` 仍是已知文件内的原文摘录；[用法和观测](agent-cli-pruning.zh-CN.md)另行记录。

已有[合成语料的 CLI 功能检查](agent-cli-search-evaluation.json)，验证中英文入口、完整文本、数字、出处、布局、缓存、范围和错误处理。它们没有人工相关性标注，不构成下文的检索质量或 Agent 对照实验。

## 是否值得做

值得补充，让 Agent 从一个目录中找到相关文件，再取得可核对的原文片段和出处。建议先交付完整文本抽取、分块、关键词/BM25 搜索与证据返回，再把小型 embedding 作为按需组件，引入向量检索和排名融合。仅靠 BM25 或字符串相似度时，应明确描述为词项检索，不能承诺理解任意同义表达或跨语言问题。

建议流程：目录发现 → 共享 WASM 提取完整文本与结构 → 保留出处的分块 → 关键词/BM25 与可选向量召回 → 排名融合（可先评估 RRF）→ 返回文件、原文片段和定位信息。先检索，再按调用方预算裁剪上下文；不能把 `prune` 选中的少量内容作为唯一索引，否则会主动丢失事实。

返回结果应包括路径、文件版本或内容哈希、原文片段、提取文本偏移、排名和匹配方式。有真实页码、坐标、工作表或逻辑结构时一并返回；缺失时明确缺失。排序分数不等于置信度。文件删除或修改后，旧索引不能继续充当当前文件的证据。

解析、阅读顺序、布局与文档分块继续放在前端共享 WASM 核心。宿主负责目录遍历、索引持久化和可选模型运行时，不能另写格式解析器。embedding 不需要生成式 LLM，但仍需要模型、推理资源和下载；保持 Lite 无模型，按需安装后才启用向量检索。

## 能否优于现有工具

目前没有语义产品优劣的实测结论；与纯文本工具的局部对照见[本轮测量](agent-cli-search-benchmark.zh-CN.md)。公开的 [zvec-grep README](https://github.com/zvec-ai/zvec-grep/blob/891497fa87d3e03d0c9273fed0ba3e75af62f179/README.md) 已描述 ripgrep、BM25、向量组成的混合检索，以及文档解析和出处能力，不能把它当成“只有向量”的弱基线，也不能把 PDF、Office 或出处当成 FiLens 已证明独有的优势。这里固定参考提交 `891497fa87d3e03d0c9273fed0ba3e75af62f179`；尚未运行该工具。

`rg-find` 的具体实现未确认，评价时应记录实际工具、版本和命令；下文的 `rg` 是可复现的精确搜索基线，不代表某个未确认工具的全部能力。

| 用户任务 | 应检验的假设 |
| --- | --- |
| 精确查找文件名、错误码、型号、金额 | `rg` 等精确工具可能更快、更准确；混合搜索是否保留精确匹配能力？ |
| 中文改写、同义词、英文问题查中文文件 | embedding 是否增加有效召回，代价是多大模型和多少延迟？ |
| PDF、Office、扫描件、表格 | 实际解析和 OCR 能否读对关键事实？两边都允许使用文档提取，不能让 `rg` 直接搜二进制来制造优势。 |
| 版本、否定条件与相似数字 | 检索是否把旧版本或仅差一位的金额排在正确证据前面？ |
| Agent 最终解决问题 | 检索收益是否转化为更高完成率、更少上下文或更低总耗时？ |

## 三层对照

### 1. 只比较检索

冻结同一批标准化文本、相同文档 ID、相同分块和出处映射。比较精确词项基线、BM25、向量、混合检索。算法对照使用相同 embedding 模型、维度、归一化与检索预算；某工具无法接受统一分块或模型时，单独报告其默认配置，不把差异归因于某一种算法。

精确搜索可比较文件命中、召回、耗时和返回量；它没有语义排序时，不应把任意文件遍历顺序当成语义排名。只有具备明确排序的运行才报告 MRR、nDCG，或明确说明额外使用的排序规则。

这一层回答“同样读到了这些内容，谁找得更准”，避免把解析质量混进排序结论。

### 2. 从原始文件到证据

把同一批原始文件交给各工具的完整流程，分别运行产品默认配置和受控配置。`rg` 基线可使用同一份预提取文本，提取成本计入并单列。PDF、Office、图片和代码都应有，不能仅挑某工具擅长的格式。

分别记录文件支持率、抽取完整度、关键文字/OCR 错误、检索命中和出处正确性。解析失败既计入端到端失败，也单独归因，不能只对双方成功的文件算一个漂亮分数。输出页码和矩形不代表定位正确，需对照原页或人工标注检查。最终文件排名按文件 ID 去重，避免同一文件的多个块占满 top-k。

这一层回答“用户给的是这些文件，最终能否拿到正确证据”。

### 3. Agent 完整任务

使用同一个 Agent 模型及固定版本、提示、最大上下文、工具调用上限和时间预算，只替换搜索工具及必要的调用说明。对同一任务配对运行，多次重复并报告次数，交错运行顺序，降低缓存和服务波动的影响。

评价最终任务完成率、引用证据正确率、工具调用次数、输入/输出 token 和总耗时。准备索引、下载模型的成本单列，同时给出首次使用总耗时，不能只展示预热后的查询。参考答案、评审材料和实验报告必须放在可搜索目录之外，防止答案泄漏。人工评审隐藏工具名称。

这一层回答“它是否真的让 Agent 更有效”。

## 数据与问题

起步可用 100–300 份有许可的公开/合成文档、100–200 条人工标注问题；这只是起始规模，不能据此保证统计显著。按文档家族划分调参与留出测试集，同一文件的 PDF、DOCX、扫描版本及近重复内容归为同一家族。记录语料哈希，冻结后再运行所有工具。

每条问题标注相关文件、相关程度（无关/部分相关/直接回答）、必需证据与可接受出处；多文件问题标注全部必需文件，无答案问题单独标记。用各工具结果的合并池补充人工标注，隐藏来源，减少只按某一个工具的结果制作标准答案的偏差；未评审条目应标为未知，不能直接认定无关。

| 问题示例 | 检验点 |
| --- | --- |
| “谁需要批准新增开销？”；原文写“新增支出必须由负责人张三审批” | 同义改写、人物与职责 |
| “发版前还有哪种系统没验证？” | 原文中的 Windows 待验证事项，避免只匹配“发版” |
| “允许未经 Windows 验证直接正式发布吗？” | 否定条件，不能只命中同主题段落 |
| “Who must approve additional spending?”；答案只在中文文件中 | 跨语言召回 |
| 查 `FILENS2026`，混入 `FILENS2027`；查 `12345.67`，混入 `12345.76` | 标识符和数字精确性 |
| “去年这个项目预算是多少？”；语料只有今年预算 | 无答案与时间干扰 |
| 同一条款分别出现在正文 PDF、扫描页、表格和旧版附件中 | OCR、表格、版本与出处 |
| “找出批准预算与交付条件的全部文件” | 多个相关文件，不能只找对其中一个 |

上表是待标注的问题类型，不是已经通过的案例。现有 497 字摘录演示只能验证摘录行为，不能充当跨文件搜索成绩。

## 指标与判定

| 维度 | 报告方式 |
| --- | --- |
| 文件发现 | File Hit@1/5/10：前 k 个文件是否至少有一个相关文件；Recall@5/10：多个相关文件找回的比例。单独报告各问题类型。 |
| 排序 | MRR@10 衡量首个相关文件的名次；nDCG@10 使用人工相关程度评分。先合并同文件分块，再计算文件排名。 |
| 证据 | 正确文件内是否命中人工标注证据；定位偏移、页码及坐标是否与原文对应，单位和容差在运行前固定。另报过大上下文，避免靠返回全文“命中”。 |
| 无答案 | 有明确拒答/空结果策略时，报告误报率与有答案召回率；没有该机制时，标明总会返回候选，不能称为能识别无答案。阈值只能在调参集选择。 |
| 性能 | 冷/热查询 p50/p95、建索引时间、下载大小/时间、首次使用总耗时、峰值 RSS、索引体积。说明冷/热缓存定义和超时。 |
| 更新 | 新增、修改、删除后的更新时间与陈旧结果率，检查旧出处是否仍被返回。 |
| Agent 效果 | 配对任务完成率、证据正确率、工具调用、token 和总耗时，不以检索分数代替实际完成率。 |

同一机器和资源限制下运行，记录操作系统、CPU、内存、线程数、OCR/embedding 模型及哈希、工具提交、配置、命令、随机种子和原始结果。文档处理参数也需固定或明确披露，例如 FiLens 的 OCR 最大边长 960、OpenMP 线程 2。默认配置与资源受控配置分别报告，模型下载和建索引不混入热查询延迟，也不从首次使用成本中消失。

预先选定主要指标和可接受的资源上限，对逐问题配对差值计算 bootstrap 95% 置信区间；同一家族的多个问题按家族一起采样，避免把高度相关的问题当独立样本。Agent 重复运行同样要保留配对和任务分组。公开原始结果、失败案例和全部预定指标；不能只挑有利子集。没有稳定改善、样本不足或区间过宽时，结论应为尚未证明优于基线。

## 可复用的公开评价思路

[zvec-grep 的 benchmark 说明](https://github.com/zvec-ai/zvec-grep/blob/891497fa87d3e03d0c9273fed0ba3e75af62f179/benchmarks/README.md) 已区分 retrieval-only 与 Agent 端到端评价，并列出 SWE-QA20、BEIR、DuRetrieval、Quarry 等数据及文件命中、MRR、nDCG 指标。可复用其冻结语料、隔离参考答案和固定 Agent 预算的做法，再补充 FiLens 所需的文档/OCR/布局及无答案测试。上游报告是上游自己的观测，不能当作 FiLens 已运行的对比结果。

建议交付顺序：完整文本与出处索引 → BM25/精确搜索基线和评估脚本 → 按需 embedding 与混合检索 → 留出集对照 → Agent 配对任务。完成这些观测后，才能说明在哪类任务上更好，以及要付出多少安装体积、内存和时间。
